# Swaply 匿名配送 v1 方針メモ

最終更新: 2026-06-05
位置づけ: **将来実装方針のメモ** (現時点では未実装、実装依頼ではない)

---

## 0. このメモの位置付け

本書は、Swaply の **将来機能である匿名配送 v1 の設計前提**を整理したメモである。

- 現時点では匿名配送は実装しない
- 法人化後、配送事業者 / API 連携の確認後に導入予定
- 本書は実装依頼ではなく、将来設計が後戻りしないようにするための前提固定

β1 期間 (匿名配送未実装期間) の運用・UX 方針は別文書を参照:
→ [`docs/beta1_shipping_and_anonymous_delivery_policy.md`](./beta1_shipping_and_anonymous_delivery_policy.md)

---

## 1. v1 方針 (確定)

### 1.1 匿名配送 v1 は「双方匿名」のみを前提にする

- 双方が匿名配送を希望する場合のみ、匿名配送を使う
- 「片側匿名 / 片側通常」は v1 では扱わない
- 通常配送の場合は、ユーザー同士で住所・氏名を共有して郵送する

### 1.2 v1 で扱わないこと

以下は v1 では仕様化せず、配送事業者 / API 仕様の確認後に再検討する:

- 片側匿名配送
- 片方が相手分の匿名配送手数料も負担する仕様
- Plus 会員の匿名配送手数料割引 / 無料枠
- 匿名配送対応バッジ
- 取引単位 / 発送単位の課金設計

### 1.3 取引フローの整理

交換は **A→B / B→A の 2 発送** が発生する取引であることを前提に、以下の状態を区別する:

| パターン | A の希望 | B の希望 | 採用方式 |
|---|---|---|---|
| ① 双方匿名希望 | 匿名 | 匿名 | **匿名配送 v1 を使用** (本書の対象) |
| ② 片側のみ匿名希望 | 匿名 | 通常 | v1 では未対応 → 通常配送に統一 (住所共有が必要な旨を双方に明示) |
| ③ 双方通常 | 通常 | 通常 | 既存の通常郵送フロー |
| ④ 会場 / 手渡し | — | — | 既存の会場交換 / 手渡しフロー |

② のケースでは、匿名希望側に「相手が匿名配送を希望していないため、通常配送になります。住所・氏名の共有が必要です」と明示し、合意の上で進めるか取引キャンセルかをユーザーに選択させる (v1 設計時に UX 詳細を確定)。

## 2. なぜ片側匿名を v1 で扱わないか

### 2.1 配送事業者 / API 仕様未確認

- ヤマト運輸の配送連携 API
- 日本郵便 e 発送サービス / プライバシー配送

これらが「片側のみ匿名配送」を許す商品 / API として提供されているかは現時点未確認。一般的な C2C 匿名配送商品は「双方の個人情報が事業者経由で秘匿される」前提の設計であり、片側のみ匿名 (= 片側だけ住所が事業者に渡る非対称運用) を許すかは事業者問い合わせ後に判明する。

### 2.2 アプリ / DB 上は表現できても、配送事業者の現実が違う可能性

- アプリ・DB 上は発送 (`shipments`) 単位で匿名 / 通常を保持できる
- しかし、配送商品 / API レベルで片側匿名が許されないと、アプリ上の表現と実運用が乖離する
- 先に「片側匿名対応」を仕様化すると、後で配送事業者連携時に破綻する可能性

### 2.3 ユーザー誤解・トラブルリスク

- 「匿名配送」と UI 表示したのに、実際は片側だけ住所共有が発生する
- ユーザーの期待値ズレ → 通報・離脱・SNS 炎上
- 「住所を出したくないからこそ Swaply を使った」というユーザーには致命的な信頼毀損

### 2.4 v1 を「双方匿名のみ」に絞る効果

- 配送事業者連携の選択肢が広がる (双方匿名商品は事業者の標準ラインに揃いやすい)
- UI / DB / 規約の設計がシンプルになる
- ユーザーへの説明も「双方が同意すれば匿名で交換できる」と明快
- 片側匿名のニーズは、配送事業者仕様確認後に再検討する余地を残す

## 3. 将来検討事項 (v1 以降)

配送事業者 / API 仕様の確認結果に応じて、以下を順次検討する:

### 3.1 片側匿名配送 (v2 以降検討)
- 配送事業者が片側匿名を許す商品 / API を提供している場合のみ
- 片側だけが住所共有を許容するパターンの UX 設計

### 3.2 相手分負担方式
- 一方が「相手の匿名配送手数料も負担する」ことで、相手の心理的負担を下げる
- 提案時オプション (例: 「私が双方の匿名配送手数料を負担します」) として実装可能性

### 3.3 Plus 会員の匿名配送特典
- 匿名配送手数料の割引 / 無料枠 / 月次上限
- Plus 加入インセンティブ設計
- `constants/feature-flags.ts:BILLING_ENABLED` の Phase 3+ 有効化と連動

### 3.4 匿名配送対応バッジ
- 出品 / プロフィールに「匿名配送対応」バッジを表示
- 匿名配送希望ユーザー同士のマッチング率向上を狙う UX
- ただし、片側だけバッジが付いている状態をどう扱うかは v2 以降の片側匿名仕様と連動

### 3.5 課金単位
- 取引単位 (1 trade = 1 課金) / 発送単位 (1 shipment = 1 課金) のどちらを採用するか
- A→B / B→A の 2 発送ある取引で、課金体系を双方納得感のある形にする

## 4. β1 との関係

β1 では匿名配送は完全未実装。本書 v1 方針はその先 (Phase 1.5 または Phase 2) の本格実装時の前提を固定するもの。

β1 期間中の方針 (準備中表示 / 待ち登録 / 通常郵送の UX 等) は引き続き
[`docs/beta1_shipping_and_anonymous_delivery_policy.md`](./beta1_shipping_and_anonymous_delivery_policy.md) を Source of Truth とする。

本書と β1 文書の関係:

```
β1 期間
  ↓
  beta1_shipping_and_anonymous_delivery_policy.md
    - 匿名配送 = 準備中表示 + 待ち登録
    - 通常郵送 = 住所共有あり、UX で明示
    - 会場 / 手渡し = 既存フロー
  ↓
  配送事業者問い合わせ + 法人化 + API 連携確認
  ↓
v1 実装期 (Phase 1.5 or Phase 2)
  ↓
  anonymous_shipping_policy.md (本書)
    - 双方匿名のみ
    - 片側匿名は v2 以降検討
    - 課金 / 特典は配送事業者仕様確認後に確定
```

## 6. 収益位置づけ (★ 確定方針)

> **匿名配送は、Swaply の将来機能として重要だが、収益の柱として見ない。**

匿名配送の主目的は次の通り:

> 匿名配送 = 収益源ではなく、郵送交換の参加障壁を下げる安全装置

主目的は、住所共有への不安を下げ、**郵送交換の成立率・継続率・信頼性を上げること**。

### 6.1 なぜ収益柱として見ないか

#### (a) ユーザー負担は手数料だけではない

推し活グッズ交換は、現状 X 上で普通郵便 / ミニレター等による交換が **無料文化に近い形** で成立している。匿名配送を使う場合、ユーザー負担は Swaply 手数料だけでなく:

```
通常郵送:
  普通郵便 / ミニレター等
  1 発送あたり約 100 円前後

匿名配送:
  追跡付き配送実費
  + Swaply 匿名配送手数料
```

交換は **A→B / B→A の 2 発送が発生** するため、手数料を高くしすぎると、1 交換あたりの追加負担が大きくなる。結果、ユーザーは無料の X 交換 / 通常郵送に戻る可能性がある。

#### (b) 双方匿名限定による利用率の構造的制約

本書 §1 の通り、Swaply v1 では「双方が匿名配送を希望する場合のみ匿名配送を使う」前提。
匿名配送利用率は構造的に高くなりにくい。

例:
```
ユーザー A の匿名希望率: 40%
ユーザー B の匿名希望率: 40%
双方が匿名希望になる確率: 0.4 × 0.4 = 16%
```

→ 「匿名配送利用率 50-70%」のような前提は **置かない**。

### 6.2 利用率の仮説レンジ (確定)

| レンジ | 評価 |
|---|---|
| 5-10% | 低め |
| **10-20%** | **基本レンジ (本書の前提)** |
| 25-30% | かなり強い |
| 50% 以上 | 特殊条件を除き非現実的 |

売上試算は **10-25% を基本レンジ** とする。50% 以上の利用率は前提にしない。

## 7. 価格仮説 (★ 確定方針)

> **匿名配送手数料は、収益最大化ではなく利用率最大化を優先する。**

### 7.1 1 発送あたりの手数料仮説

| 価格 | 位置付け |
|---|---|
| **100 円 / 発送** | **本命** |
| 150 円 / 発送 | 上限候補 |
| 200 円 / 発送以上 | 初期には重い (採用しない方向) |

### 7.2 1 交換あたりの Swaply 売上 (双方匿名 = 2 発送)

| 1 発送価格 | 1 交換売上 |
|---|---:|
| 100 円 | 200 円 / 交換 |
| 150 円 | 300 円 / 交換 |
| 200 円 | 400 円 / 交換 |

配送実費は別途ユーザー負担。ユーザー体感では「Swaply 手数料」単独ではなく **「通常郵送との差額」** で判断される。

### 7.3 売上試算の基本方針

**匿名配送手数料だけで大きな売上を作る前提は置かない。**

100 円 / 発送、双方匿名で 200 円 / 交換の場合:

| 月間成立数 | 利用率 10% | 利用率 25% |
|---:|---:|---:|
| 1,000 件 | 月商 20,000 円 (100 交換) | 月商 50,000 円 (250 交換) |
| 5,000 件 | 月商 100,000 円 (500 交換) | 月商 250,000 円 (1,250 交換) |
| 10,000 件 | 月商 200,000 円 (1,000 交換) | 月商 500,000 円 (2,500 交換) |

→ **匿名配送は収益柱ではなく、成立率・継続率・信頼性向上のための補助機能**として扱う。

## 8. Plus 設計との関係 (★ 確定方針)

将来 Plus を導入する場合も、**匿名配送手数料の無料枠を主価値にしすぎない**。
理由: per-use 収益 (1 発送 100 円) と Plus 無料枠 (定額) がカニバる可能性。

### 8.1 現時点の Plus 仮説

| 項目 | 仮説 |
|---|---|
| Plus 月額 | 300 円前後 |
| 匿名配送特典 | **無料枠ではなく割引を基本** |

例:
```
通常ユーザー: 匿名手数料 100 円 / 発送
Plus ユーザー: 匿名手数料 50 円 / 発送
```

### 8.2 Plus の主価値候補

匿名配送手数料の割引は Plus の一要素であり、主価値ではない。Plus の主価値候補:

- 匿名配送手数料の割引
- 匿名配送対応バッジ
- 優先サポート
- 発送リマインド強化
- 将来機能の先行利用

匿名配送の無料枠を Plus 特典として付ける場合は per-use 収益とのカニバリゼーションを慎重に検討する。
